Firewall today

The legacy FORWARD rules still accept every flat network in both directions. The second line of each pair allows new connections to that network from any source, including another bridge, which is why separate bridges alone isolated nothing.

# roles/security/templates/firewall.sh.j2
iptables -P FORWARD DROP
iptables -A FORWARD -m conntrack \
  --ctstate ESTABLISHED,RELATED -j ACCEPT
# repeated for every legacy network:
iptables -A FORWARD -s 10.89.0.0/24 -j ACCEPT   # egress
iptables -A FORWARD -d 10.89.0.0/24 -j ACCEPT   # "return"

The zone rules are loaded ahead of those accepts, in audit mode: they log zone-would-deny and still accept, so nothing changes until a zone is enforced. They are checked with real packets in a throwaway namespace (scripts/check-firewall-netns.sh).

  • Same-bridge traffic now reaches netfilter, because br_netfilter is on (persisted at boot). That is what lets the capture see pod-to-pod flows at all; without it the capture saw none.
  • The ops dashboard still mounts the host's root SSH key. It is effectively root on the host and still shares the flat network with everything.
  • Traefik internal-only was tightened on 2026-08-28 to cloudflared, the bridge gateway and loopback.

Each pod joins one zone network. Traffic inside a zone is free (the generated rules accept it explicitly). Traffic between zones is dropped unless a line in flows.yml allows it. Four zones hold exactly one pod on purpose: the tunnel, the edge, the ops dashboard and Mail Kit.

Firewall in the target state

Every packet that touches a zone address jumps into a generated chain first. That chain always ends in a decision, so a zone packet never reaches a legacy accept.

# GENERATED from network/zones.yml + flows.yml
iptables -N ZONE_FWD ZONE_AUDIT ZONE_DENY
# anti-spoof: only a zone's own addresses may enter its bridge
iptables -A FORWARD -i br-mail ! -s 10.89.128.168/29 -j ZONE_DENY
# every zone packet is decided in ZONE_FWD, before legacy accepts
iptables -A FORWARD -s 10.89.128.0/24 -j ZONE_FWD
iptables -A FORWARD -d 10.89.128.0/24 -j ZONE_FWD

# traffic inside a zone is free
iptables -A ZONE_FWD -s 10.89.128.16/28 -d 10.89.128.16/28 -j ACCEPT
iptables -A ZONE_FWD -s 10.89.128.2/32 -d 10.89.128.10/32 \
  -p tcp --dport 443 -j ACCEPT   # tunnel -> traefik only

# enforced zones: drop and log. audit zones: log and accept
iptables -A ZONE_FWD -j ZONE_AUDIT   # "zone-would-deny "

Host access is a separate, narrow set of INPUT rules, each tied to one bridge and one pod address:

iptables -A INPUT -i br-tunnel -s 10.89.128.2/32 \
  -p tcp --dport 22 -j ACCEPT   # ssh.<domain> tunnel origin
iptables -A INPUT -i br-mgmt -s 10.89.128.162/32 \
  -p tcp --dport 22 -j ACCEPT   # ops dashboard control path
  • Bridges are named, not discovered. podman network create --interface-name br-mgmt, so rules can refer to a bridge before its first pod starts.
  • Names do not cross zones. A pod resolves only its own network's names, so each pod gets --add-host entries for exactly the destinations it may reach, generated from the flows file.
  • Pod names, never container names. A pod member's own name does not resolve, which is why every consumer was repointed at the pod (the honeypot batch found a scrape target that would have died silently).
  • Honest limit. A compromised dashboard still holds a host-root key. The zone narrows who reaches it; restricting the key itself is an open decision.

Audit first, enforce one zone at a time

1 · audit

Rules log zone-would-deny and still accept. At least 7 days of real pod-to-pod capture, spanning a Sunday prune, the 02:00 backup and the 03:00 / 03:30 / 04:40 jobs. The useful clock started 2026-10-25 07:08, when br_netfilter made pod-to-pod flows visible.

2 · review

Every distinct source, destination and port is added to flows.yml or recorded as traffic to drop. Zero unexplained entries for 48 hours. Rollback rehearsed. A second reader re-checks the diff.

3 · enforce

One zone flips to enforce, then 24 hours of watching zone-deny and the health checks. Any surprise reverts that zone to audit first.

  9. net-agent, net-svc, net-frontendBots, chat, and internal services.
  10. net-observe last, scrape converted to pushA scraper that reaches every zone defeats the segmentation, so each zone pushes instead.

Decided

  • Zones are /29 and /28 from 10.89.128.0/24; static pod addresses.
  • One pod per hostile-facing or credential-holding service: the honeypot and threat-map are separate pods because a shared pod would put an attacker's foothold next to the CrowdSec key and reports token.
  • Static sites get a pod each, not one shared nginx: they all bind :80.
  • Cloudflared and Traefik live in separate single-pod zones; ssh.<domain> stays on the tunnel.
  • The ops dashboard runs alone in net-mgmt; Mail Kit runs alone in net-mail.
  • Only ansible-deployment stays standalone.
  • Audit before enforce, one zone at a time, never before the capture review.
